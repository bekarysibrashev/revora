# Revora 1C Extension v18.3

`RevoraExtensionReady-v18.3-complete-sync.zip`
SHA-256: `960da358744c7e4c27c60fa4f30da97899a27326621fe936e7e5f4d9bc5beb57`

Ревизия диагностическая. Ни одна формула метрики не изменена, поэтому числа,
которым клиника уже доверяет, останутся прежними. Меняется только то, что
расширение о них рассказывает — и то, что оно отказывается делать молча.

## Зачем это нужно

При ручной синхронизации за 04.08.2026–05.08.2026 разрез начисленной выручки
по врачам разошёлся с итогом клиники примерно на 1 973 820,35 KZT, а разрез
оплаченной — примерно на 1 874 920,35 KZT. Причина расхождения в самих данных
не искалась, потому что её там может и не быть: в `СформироватьВыручкуПоУслугам`
итог клиники и разрезы приходили из **двух разных вычислений**.

```bsl
// разрезы по филиалам и специализациям считались прямым запросом
ИтогоСтоимость = ИтогоСтоимость + Число0(Выборка.Стоимость);
...
// а итог клиники затем ПЕРЕЗАПИСЫВАЛСЯ скрейпом штатного отчёта
ИтогоСтоимость = ПолучитьИтогВыручкиИзШтатногоОтчета(НачалоПериода, КонецПериода);
```

Комментарий рядом это признавал: «прямой Запрос не воспроизводит его итог
полностью». Разница между двумя числами никуда не сохранялась — её нельзя было
ни увидеть, ни объяснить, ни опровергнуть.

## Что изменено

**1. Подстановка периода больше не может провалиться молча.**
`СтрЗаменить` при несовпадении шаблона возвращает исходный текст, параметры
`&НачалоПериода`/`&КонецПериода` в запросе не появляются, а
`УстановитьПараметр` для несуществующего параметра ошибки не вызывает.
Виртуальная таблица оборотов тогда отрабатывает **по всей истории**, и разрез
оказывается кратно больше итога — распознать это по цифрам постфактум почти
невозможно. Теперь подстановка идёт через `ПодставитьПериодВЗапрос`, которая
выбрасывает исключение, если шаблон не найден. Затронуты три места:
`ОказанныеУслугиПоВрачу`, `АнализОплатПоВрачам` и
`ПациентыПосетившиеКлиникуЗаПериод` — последнее нашлось попутно и имело ту же
уязвимость.

**2. Оба итога сохраняются, разница отправляется как факт.**
Итог клиники по-прежнему берётся из строки ИТОГО штатного отчёта — ровно так
же, как раньше. Но сумма строк прямого запроса больше не затирается, и в
снимок уходит:

| Поле `summary` | Что означает |
|---|---|
| `clinic_total_report` | итог из строки ИТОГО штатного отчёта (то, что отправлялось и раньше) |
| `clinic_total_query` | сумма строк прямого запроса, которой посчитаны разрезы |
| `clinic_total_difference` | разница между ними |

**3. Строка ИТОГО теперь видна целиком.**
Скрейп берёт «второе число в строке ИТОГО», предполагая, что первое —
количество, а второе — стоимость. Если в макете отчёта есть ещё одна числовая
колонка (цена без скидки, средний чек, служебный код), это предположение
возвращает чужое число. Поведение не изменено, но теперь в снимок уходит:

| Поле `summary` | Что означает |
|---|---|
| `total_row_numeric_columns` | сколько числовых колонок реально было в строке ИТОГО |
| `total_row_column_taken` | номер колонки, из которой взято значение |
| `total_row_numbers` | все числа строки ИТОГО по порядку |

**Это и есть главный смысл ревизии.** После первой же синхронизации станет
однозначно понятно, какая из двух гипотез верна:

- если `total_row_numeric_columns` больше 2 и в `total_row_numbers` видно, что
  взятое число не совпадает со стоимостью — расхождение объясняется скрейпом
  не той колонки, и лечится сменой правила выбора колонки;
- если колонок ровно 2 и взятое число — действительно стоимость, то отчёт и
  регистр `Продажи` реально расходятся, и разбираться нужно уже в составе
  документов (возвраты, сторно, строки без сотрудника, отборы СКД).

**4. Продажи без врача теперь названы.**
Строки с незаполненным `Сотрудник` уезжали с пустым наименованием. Теперь они
приходят как «Не указано», и Revora считает их отдельно
(`unattributed_total`), не смешивая с необъяснённой разницей.

## Что НЕ изменено

- Формулы всех метрик.
- Способ получения итога клиники (та же строка ИТОГО того же отчёта).
- Регламентное задание: по-прежнему поставляется выключенным (`Use=false`),
  почасовая синхронизация не включается.
- Формы, роли и остальные объекты расширения: проверено программно — в архиве
  изменились ровно две записи, `CommonModules/РвОбменСервер/Ext/Module.bsl` и
  `Configuration.xml`, все остальные 24 байт в байт совпадают с v18.2.

## Установка

1. В Конфигураторе открыть расширение `Revora`.
2. `Конфигурация → Загрузить конфигурацию из файлов…` для открытого расширения,
   указать распакованную папку v18.3 — как при обновлении на v18.2.
3. `Конфигурация → Проверка модулей`.
4. Применить изменения.
5. Выполнить **короткую** ручную синхронизацию за один-два дня.
6. Открыть в Revora карточку синхронизации и посмотреть новые поля
   `total_row_numbers` и `clinic_total_difference` — этого достаточно, чтобы
   определить причину расхождения.
7. Только после этого загружать данные за год помесячно, начиная с января.

Статические проверки ZIP/XML/UTF-8, баланса `Функция`/`КонецФункции` и
неизменности остальных объектов архива не заменяют проверку модулей в реальном
Конфигураторе.

## Известное ограничение этой ревизии

Пакетная выгрузка для годовой загрузки **не** переделана. Сейчас полный реестр
пациентов отправляется один раз за запуск `СинхронизироватьПериод` (внутри
одного запуска он по дням не дублируется), но при помесячной загрузке за год
он уйдёт 12 раз. Отправка идемпотентна — дубликатов пациентов не возникнет,
приём делает upsert по `external_id` — но это лишние 12 × 20 804 записи по
сети. Отдельный переключатель «отправлять полный реестр пациентов» требует
правки модуля формы и контракта синхронизации; делать это наполовину хуже, чем
не делать, поэтому оно вынесено в отдельную задачу.
