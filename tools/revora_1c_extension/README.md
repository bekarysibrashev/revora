# Revora_Обмен для 1С:Медицина. Стоматологическая клиника 2.1

Исходники расширения, которое рассчитывает те же показатели, что семь
контрольных отчётов 1С, и отправляет контрольные и дневные снимки в Revora.

Поддерживаемая база пилота:

- платформа 1С 8.3.27.1936 (расширение собрано с `ConfigurationExtensionCompatibilityMode = Version8_3_21`, так что подойдёт любая платформа 8.3.21+);
- конфигурация «1С:Медицина. Стоматологическая клиника», редакция 2.1;
- версия конфигурации 2.1.34.1.

Расширение не изменяет основную конфигурацию и не отправляет медицинские
карты, строки лечения или телефон в открытом виде. Передаются агрегаты,
идентификаторы подразделений, справочные названия врачей/специализаций и
стабильные обезличенные GUID пациентов для корректного подсчёта уникальных
пациентов в произвольном периоде.

С версии 1.2.0 (patient_phone_identity, метрики patients) дополнительно
передаётся ФИО пациента и SHA-256 phone_hash телефона (сам номер телефона
в открытом виде никогда не покидает 1С -- нормализация и хэширование
происходят на стороне расширения тем же алгоритмом, что и в Revora).
Это подтверждено политикой хранения данных клиники: ФИО и хэш телефона
остаются внутри Revora и используются только для сопоставления входящих
звонков/WhatsApp с существующими пациентами 1С.

С версии 1.3.0 дополнительно передаются: `appointments_transferred` (метрика
appointments, тот же лучший-по-возможности разбор текста Статус/ПричинаОтмены,
что уже используется для отмен/неявок -- ищет подстроку «перенос») и `refunds`
(метрика cash_receipts, отдельный изолированный запрос к тому же регистру
ДенежныеСредства, обёрнутый в Попытка/Исключение: при несовпадении видов
операций в конкретной базе метрика просто не отправляется, а не отправляется
приблизительной). `payroll_paid` уже отправлялся с версии 1.2.0 вместе с
`payroll_accrual`. `operating_expenses` и `insurance_payments` НЕ реализованы --
для этой типовой конфигурации не подтверждён источник (нет отдельного
перечисления/регистра для страховых плательщиков и категории операционных
расходов без ручной классификации), поэтому эти два показателя намеренно не
отправляются, чтобы не передавать угаданную цифру; соответствующие карточки
Revora останутся честно «Не хватает данных» до подтверждения источника. По
той же причине не реализованы загрузка врачей и загрузка кабинетов.

## Состав

- `РвОбменСервер.bsl` — исходный текст серверного модуля (для чтения/диффа,
  тот же текст уже встроен в `.zip` ниже);
- **`RevoraExtensionReady-v13.zip`** — актуальный, полностью готовый к загрузке
  пакет исходников расширения версии **1.3.0**: полный XML-каркас (роль,
  подсистема, общая форма настроек, общая команда, общий модуль) плюс
  обновлённый `РвОбменСервер.bsl` внутри. Используйте этот файл;
- `RevoraExtensionReady-v12.zip` — предыдущая версия (1.1.0, без Task 1/2),
  оставлена для истории/отката, использовать для новых установок не нужно;
- `RevoraExtensionSource.zip` — самый первый черновой каркас (до v2);
- backend endpoints: `POST /api/v1/integrations/1c/report-snapshot` для
  контрольных итогов и `POST /api/v1/integrations/1c/report-snapshots/batch`
  для пакетной дневной выгрузки;
- авторизация: существующий connector token Revora.

## 1. Как установить v13 (с нуля)

1. Скопируйте `RevoraExtensionReady-v13.zip` на компьютер клиники и
   распакуйте в отдельную папку (Конфигуратор загружает исходники из папки
   с файлами, а не сам `.zip`).
2. Откройте базу в Конфигураторе → «Конфигурация» → «Расширения» →
   «Добавить» → «Загрузить из файлов» → укажите распакованную папку.
3. Конфигуратор соберёт `.cfe` расширения автоматически. Сохраните и
   обновите конфигурацию базы данных (F7 / «Обновить конфигурацию базы
   данных»).
4. Проверьте версию (см. пункт 3 ниже) — должна быть **1.3.0**.

## 2. Как заменить предыдущую версию (v11/v12 уже установлена)

1. В Конфигураторе: «Конфигурация» → «Расширения» → выделите старую
   `Revora` → «Обновить из файлов» → укажите папку, распакованную из
   `RevoraExtensionReady-v13.zip`.
2. Конфигуратор сам заменит все объекты расширения (модуль, форму, команду,
   роль, подсистему) на версию из v13 — ничего удалять/пересоздавать вручную
   не нужно, идентификаторы объектов (`uuid`) в v13 совпадают с v12.
3. Сохраните и обновите конфигурацию базы данных.

## 3. Где посмотреть версию расширения

- В Конфигураторе: «Конфигурация» → «Расширения» → колонка «Версия» у
  строки Revora должна показывать **1.3.0**.
- В самой 1С (толстый/тонкий клиент): раздел Revora → «Настройки обмена» →
  после нажатия «Синхронизировать» сообщение начинается с
  `Revora 1.3.0 (сервер 1.3.0-server)…`.

## 4. Где указать Revora API URL

Раздел Revora → команда «Настройки обмена» открывает форму с полем
«АдресAPI» (по умолчанию `https://revora-san-api-0sj5.onrender.com`).
Значение сохраняется в хранилище настроек пользователя (`Revora/Обмен`) и
подставляется автоматически при следующем открытии формы.

## 5. Где указать connector token

В той же форме «Настройки обмена» — поле «Токен». Токен выдаётся Revora на
сторону клиники заранее (тот же connector token, что и раньше, отдельный
токен для v13 не нужен).

## 6. Как выбрать период

В форме «Настройки обмена» — поля «НачалоПериода»/«КонецПериода». По
умолчанию подставляется прошлый календарный месяц. Для первого запуска
рекомендуется указать контрольный месяц целиком (весь месяц, не часть).

## 7. Как запустить snapshot

В форме «Настройки обмена» нажмите «Синхронизировать». Расширение:

1. отправит семь контрольных итогов за весь период (`report-snapshot`);
2. затем разобьёт период на дни и отправит их пакетами по 24 снимка
   (`report-snapshots/batch`) — из дневных данных Revora потом честно
   собирает любой произвольный вложенный диапазон.

Итоговое сообщение покажет количество дневных снимков и контрольные суммы
(выручка/оплата/зарплата), посчитанные прямо в 1С — их можно свериться со
значениями на дашборде Revora после синхронизации.

## 8. Как проверить, что patient_phone_identity действительно ушёл

1. В форме настроек укажите период, за который в 1С точно есть визиты
   пациентов, и нажмите «Синхронизировать».
2. В Revora на дашборде должны появиться/обновиться карточки «Пациенты»,
   «Первичные пациенты», «Повторные пациенты», «Давно не посещавшие» —
   это прямое подтверждение, что метрика `patient_phone_identity` дошла
   и была разобрана (`upsert_patient_identities`).
3. Прямая проверка на бэкенде (для разработчика): в таблице patients после
   синка должны появиться строки с непустым `phone_hash` (64 hex-символа)
   и корректными `first_visit_at`/`last_visit_at`/`visit_count`. Открытый
   номер телефона в базе Revora не хранится нигде, только его хэш.
4. Проверка обращений: позвоните/напишите в WhatsApp с номера, который уже
   есть среди пациентов 1С за этот период — новое обращение должно
   классифицироваться как `existing_1c_patient`, а не `new_contact`.

## 9. Как проверить, что отчёты вообще отправились

- В сообщении после «Синхронизировать» не должно быть текста «Ошибка:».
- На дашборде Revora карточки, зависящие от 1С (выручка, зарплата,
  пациенты, записи), должны показывать значения, а не «Не хватает
  данных», за период, который вы синхронизировали.
- Логи backend (`.runlogs/backend.stdout.log` на сервере Revora, либо
  панель логов в облаке) покажут входящие запросы на
  `/api/v1/integrations/1c/report-snapshot` и `/report-snapshots/batch`
  с кодом ответа 200/201.

## 10. Какие данные никогда не отправляются

- открытый номер телефона (только SHA-256 `phone_hash`);
- пароли/токены авторизации самой 1С;
- медицинские карты, диагнозы, строки лечения;
- показатели, которые Revora считает сама (EBITDA, валовая/операционная
  прибыль, маржинальность, CAC, CPL, ROAS, ROMI) — для них 1С никогда не
  создаёт свой `metric_code`, это всегда расчёт на стороне Revora поверх
  присланных фактов;
- `operating_expenses`, `insurance_payments`, загрузка врачей, загрузка
  кабинетов — источник в этой конфигурации не подтверждён, поэтому не
  отправляются (см. выше).

## 11. Как посмотреть ошибки

- В самой 1С: если синхронизация упала, форма покажет
  `Ошибка: <краткое описание>` — это `КраткоеПредставлениеОшибки` от
  платформы, обычно достаточно, чтобы понять причину (нет сети, неверный
  токен, таймаут).
- Более подробно: журнал регистрации 1С (Конфигуратор → «Администрирование»
  → «Журнал регистрации»), отфильтровать по имени пользователя, за которого
  запускалась синхронизация, и по времени запуска.
- На стороне Revora: неверный/просроченный `metric_code` или `report_type`
  вернётся HTTP 422 с описанием поля, которое не прошло валидацию — это
  видно в том же сообщении об ошибке в 1С (платформа показывает тело
  HTTP-ответа при неуспехе).

Первый запуск выполняется вручную за контрольный месяц. Расширение сначала
отправляет семь официальных итогов периода, затем дневные наборы на каждый
день (зарплата остаётся месячной). Backend использует точный контрольный
итог для полного месяца и дневные данные для произвольных вложенных
диапазонов.
