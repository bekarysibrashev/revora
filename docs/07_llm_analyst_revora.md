# Revora LLM AI-аналитик

## Цель

Диалоговый слой объясняет уже рассчитанные показатели Revora. Он не заменяет витрины, не вычисляет финансовые значения и не получает доступ к SQL или сырым данным пациентов.

## Поток одного сообщения

1. JWT определяет `tenant`, пользователя, роль и разрешённые филиалы.
2. Сервер проверяет владельца сессии, фиксированный `branch_id`, лимит частоты и период.
3. Телефоны, email, ИИН, UUID и явно подписанные ФИО редактируются до сохранения и отправки провайдеру.
4. Модель получает только инструменты, разрешённые роли пользователя.
5. Аргументы инструмента проходят Pydantic allowlist; `tenant_id`, `user_id` и `branch_id` модель передать не может.
6. Инструмент вызывает существующий service-слой Revora, где повторно применяются role/branch-проверки. Перед LLM из результата удаляются внутренние идентификаторы, а сотрудники получают временные псевдонимы (`Врач 1`, `Врач 2`).
7. LLM формулирует объяснение. Сервер независимо добавляет источники, период и `data_as_of`.
8. Числа ответа сверяются с числовыми значениями результатов инструментов. Неподтверждённый ответ заменяется безопасным сообщением.
9. В аудит записываются только метаданные: модель, инструменты, токены, задержка и код ошибки. Промпты и payload инструментов в audit не пишутся.

## Threat model

- **Cross-tenant access:** PostgreSQL RLS + tenant из подписанного JWT + фильтры repository/service.
- **Подмена филиала:** `branch_id` хранится в сессии; отсутствует в tool schema; лишние аргументы запрещены.
- **Prompt injection:** пользовательский ввод считается недоверенным, известные попытки блокируются до LLM, инструменты остаются allowlist/read-only независимо от текста.
- **Произвольный SQL:** SQL-инструмента нет; LLM видит только JSON Schema аналитических функций.
- **Утечка PII:** агрегированные инструменты не возвращают пациентов; телефон/email/ИИН/UUID и подписанные ФИО в вопросе редактируются; ФИО и ID сотрудников удаляются из tool payload.
- **Галлюцинация чисел:** детерминированные сервисы считают показатели, numeric grounding сверяет ответ.
- **DoS/стоимость:** максимум сообщений в минуту, ограничение длины, периода, числа tool-rounds, output tokens и timeout.
- **Сбой провайдера:** нормализованные коды ошибок без раскрытия ключа или тела ответа.

## Конфигурация

`OPENAI_API_KEY` хранится только в backend runtime. По умолчанию используется `gpt-5.6-terra` как баланс качества и стоимости; модель меняется через `OPENAI_MODEL` без изменений бизнес-кода. Интеграция использует Responses API, `store=false`, strict function tools и стабильный privacy-preserving `safety_identifier`.

Официальные основания: [OpenAI model guidance](https://developers.openai.com/api/docs/guides/latest-model) рекомендует Responses API для tool-using multi-turn workflows и советует открывать только релевантные инструменты; [GPT-5.6 model catalog](https://developers.openai.com/api/docs/models) описывает Sol/Terra/Luna и поддержку function calling.

## Критерии приёмки

- пользователь видит свои сессии и историю;
- роль не может вызвать запрещённый инструмент;
- модель не может изменить tenant/user/branch scope;
- в LLM не передаются raw patient rows и распознаваемые телефон/email/ИИН;
- каждый аналитический ответ содержит независимые источники, период и свежесть;
- неподтверждённые числа не возвращаются пользователю;
- prompt injection, invalid tool args, timeout, rate limit и отсутствие ключа имеют тестируемые ошибки;
- backend tests и production frontend build проходят.
